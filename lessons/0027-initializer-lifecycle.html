Initializer：把一次性启动逻辑从 Hooks 拆出来

Initializer 是 Loco 独有的生命周期组件：它可以在启动前做一次初始化、在路由完成后继续改造 Router，还能接入 cargo loco doctor 健康检查。

1. 当前版本的真实顺序

after_context(ctx)
    ↓
Hooks::before_run(ctx)
    ↓
Hooks::initializers(ctx)
    ↓
initializer.before_run(ctx)      // 每个 initializer
    ↓
before_routes → routes.to_router  // 路由 + MiddlewareLayer
    ↓
Hooks::after_routes(router, ctx)
    ↓
initializer.after_routes(router, ctx)
    ↓
serve / worker / scheduler

关键差异：Initializer 的 before_run 和 after_routes 都有独立的错误返回值；它不是一个只能返回 Vec 的简单回调。

2. 定义一个 initializer

use loco_rs::{
    app::{AppContext, Initializer},
    doctor::{Check, CheckStatus},
    Result,
};

struct PaymentsInitializer;

#[async_trait]
impl Initializer for PaymentsInitializer {
    fn name(&self) -> String {
        "payments".to_owned()
    }

    async fn before_run(&self, ctx: &AppContext) -> Result<()> {
        // 例如：预热一个客户端，或验证 SharedStore 中的依赖
        if !ctx.shared_store.contains::<PaymentClient>() {
            return Err(Error::Message("PaymentClient missing".into()));
        }
        Ok(())
    }

    async fn check(&self, _ctx: &AppContext) -> Result<Option<Check>> {
        Ok(Some(Check {
            status: CheckStatus::Ok,
            message: "payments initializer ready".into(),
            description: None,
        }))
    }
}

check 会被 cargo loco doctor 调用；它适合检查连接配置、必需依赖和外部服务可达性。不要把每个请求都做的逻辑放进 initializer。

3. 在 App 中注册

async fn initializers(
    _ctx: &AppContext,
) -> Result<Vec<Box<dyn Initializer>>> {
    Ok(vec![Box::new(PaymentsInitializer)])
}

把它放进 impl Hooks for App。Loco 会记录 initializer 名称，并在适当的启动阶段调用它。

4. 什么时候用哪个 Hook

扩展点选择它的理由
after_context替换 AppContext 字段，或把服务放入 SharedStore
before_run一次性预热，适用于所有运行模式
Initializer::check让 cargo loco doctor 检查你的依赖
Initializer::after_routes在路由构建后再接入 Axum 逻辑
