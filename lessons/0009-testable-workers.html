让 Worker 可测试：HTTP 202、job id 与执行模式

目标：把第八课的 Worker 接到一个受保护的 POST 接口，并写一个不会竞速的请求测试。

1. HTTP 接口只负责入队

慢任务不应该让请求一直等到下载完成。接口收到请求后，验证身份和参数，调用 perform_later，然后用 202 Accepted 告诉客户端“已接受，正在处理”。

use crate::workers::downloader::{DownloadWorker, DownloadWorkerArgs};

#[debug_handler]
pub async fn enqueue_download(
    _auth: auth::JWT,
    State(ctx): State<AppContext>,
    Path(pid): Path<String>,
) -> Result<Response> {
    let job_id = DownloadWorker::perform_later(
        &ctx,
        DownloadWorkerArgs { user_guid: pid.clone() },
    ).await?;

    Ok((
        StatusCode::ACCEPTED,
        Json(serde_json::json!({ "job_id": job_id, "user_guid": pid })),
    ).into_response())
}

路由放在 admin.rs::routes()：

.add("downloads/{pid}", post(enqueue_download))

2. 为什么测试环境用 ForegroundBlocking

模式调用 perform_later 后测试意义
ForegroundBlocking当前流程执行完 Worker断言副作用最稳定
BackgroundAsync同进程异步执行开发方便，断言可能竞速
BackgroundQueue交给持久化队列生产环境，可跨重启

第八课的项目已经在 config/test.yaml 使用 ForegroundBlocking。所以测试里调用 perform_later 后，Worker 已经跑完，才会返回 job id。

3. 动手写请求测试

  1. 给 admin.rs 加上上面的 handler 和路由。
  2. 在 tests/requests/admin.rs 新增测试：用 prepare_data::init_user_login 拿 token 和 pid，请求 POST /api/admin/downloads/{pid}。
  3. 断言状态码是 202，响应 JSON 有非空的 job_id。
  4. 运行 cargo test --test mod requests::admin，再运行完整的 cargo test。
let body: serde_json::Value = res.json();
assert_eq!(res.status_code(), 202);
assert!(body["job_id"].as_str().is_some());
