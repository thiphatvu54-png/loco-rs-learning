API Key 认证：给机器客户端一把长期钥匙

目标：知道什么时候用 JWT，什么时候用 API Key，并看懂现有 users 表里的 api_key。

1. JWT 和 API Key 的边界

方式适合特点
JWT浏览器用户登录有 exp，可过期；签名验证
API KeyCLI、脚本、机器对机器长期凭据；数据库查 key

当前项目的 users 表已经有唯一的 api_key，模型也实现了 Authenticable::find_by_api_key。

2. 在 handler 中使用 ApiToken

use crate::models::users;

async fn current_by_api_key(
    auth: auth::ApiToken<users::Model>,
) -> Result<Response> {
    tracing::info!(user_pid = %auth.user.pid, "api key request");
    format::json(serde_json::json!({
        "pid": auth.user.pid,
        "email": auth.user.email,
    }))
}

ApiToken 会从 Authorization: Bearer <API_KEY> 读取 key，再调用 find_by_api_key 查询用户。它不使用 auth.jwt.secret、expiration 或 location 配置。

3. API Key 的风险

  • 它通常长期有效，泄露后的影响比短期 JWT 更大。
  • 只在 HTTPS 下传输，不能写进日志或提交到仓库。
  • 生产系统应提供撤销/轮换策略，数据库只存可安全管理的 key。

4. 快速练习

  1. 在一个只给机器调用的 handler 中使用 auth::ApiToken<users::Model>。
  2. 用 Authorization: Bearer <API_KEY> 发送请求。
  3. 解释为什么 auth.jwt.location 不会改变 ApiToken 的读取位置。
