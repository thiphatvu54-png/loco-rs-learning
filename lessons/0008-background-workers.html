后台任务三分法：Task、Worker、Scheduler

目标：看到一段“后台代码”时，能先判断它由谁触发，再用现有 DownloadWorker 完成一次可验证的任务。

1. 先记住触发者

机制谁触发何时用本项目证据
Task人，CLI一次性运维或手工操作src/tasks/user_create.rs
BackgroundWorker代码，请求或另一个任务HTTP 不必等待的慢工作src/workers/downloader.rs
Scheduler时钟每天、每小时等重复运行配置里运行一个 Task

判断顺序只有一句：人点一次用 Task；请求来了先返回用 Worker；到了时间自动做用 Scheduler。 Scheduler 本身不放业务逻辑，它只按时间调用一个 Task。

2. Worker 的最小骨架

当前项目已经有注册代码：

async fn connect_workers(ctx: &AppContext, queue: &Queue) -> Result<()> {
    queue.register(DownloadWorker::build(ctx)).await?;
    Ok(())
}

骨架在 src/workers/downloader.rs。参数必须能序列化，因为队列保存的是参数；传 标识符，在 perform 里重新查模型，不要把整个 Model 当快照塞进队列。

#[derive(Deserialize, Debug, Serialize)]
pub struct DownloadWorkerArgs {
    pub user_guid: String,
}

#[async_trait]
impl BackgroundWorker<DownloadWorkerArgs> for DownloadWorker {
    fn build(ctx: &AppContext) -> Self { Self { ctx: ctx.clone() } }

    async fn perform(&self, args: DownloadWorkerArgs) -> Result<()> {
        let user = users::Model::find_by_pid(&self.ctx.db, &args.user_guid).await?;
        tracing::info!(user_pid = %user.pid, user_email = %user.email, "download job ran");
        Ok(())
    }
}

调用方只负责入队：

let job_id = DownloadWorker::perform_later(
    &ctx,
    DownloadWorkerArgs { user_guid: pid.to_string() },
).await?;
tracing::info!(%job_id, "download job enqueued");

perform_later 返回的是 job id。需要跟踪、取消或重排队时保存它；不需要追踪时才明确丢弃。

不要用 tokio::spawn 代替 Worker。它不会持久化参数，也没有队列重试和可观察的 job id。慢工作应该返回错误，让队列按配置处理重试。

3. 动手：补完 DownloadWorker

  1. 在 playground\admin_api 执行 cargo loco task，确认现有的两个 Task：user:create 与 user:delete。
  2. 编辑 src/workers/downloader.rs：导入 crate::models::users，按 user_guid 调用 find_by_pid，记录一条 tracing::info!，最后返回 Ok(())。
  3. 运行 cargo fmt --check 和 cargo test。测试环境的 workers.mode 是 ForegroundBlocking，这样测试不会和后台执行竞速。
  4. 再看 config\development.yaml 的 BackgroundAsync：请求只负责入队，日志会在稍后出现。把 perform 临时改成返回 Err(Error::string("demo failure"))，观察失败日志，然后改回 Ok(())。
