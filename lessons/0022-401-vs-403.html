401 与 403：认证失败和授权失败

目标：看到错误状态码，就能判断请求卡在 JWT 身份层，还是卡在业务权限层。

1. 一句话区分

状态含义典型来源
401 Unauthorized服务端无法确认你是谁缺少、过期、错误 JWT；用户查不到
403 Forbidden已经知道你是谁，但你不能做这件事角色、资源所有权、组织权限不满足

Loco 的 JWT extractor 会在 handler 之前拒绝缺失或无效 token；JWTWithUser 找不到用户时也会返回 401。业务 handler 自己判断权限时，才进入 403 的范围。参见 JWT 官方文档。

2. 认证层：401

async fn current(
    auth: auth::JWTWithUser<users::Model>,
) -> Result<Response> {
    // 没有 token 或 token 无效时，这一行之前就已经返回 401
    format::json(&auth.user)
}

所以测试应该先写：

let response = request.get("/api/categories").await;
assert_eq!(response.status_code(), 401);

3. 业务层：403

use axum::http::StatusCode;
use loco_rs::controller::ErrorDetail;

if !auth.user.can_manage_category(&category) {
    return Err(Error::CustomError(
        StatusCode::FORBIDDEN,
        ErrorDetail::with_reason("forbidden"),
    ));
}

这里 token 已经有效，auth.user 也已经加载成功；只是业务规则不允许操作资源。错误构造方式参考 Loco 官方的 Handle errors。

4. 测试要锁住两条边界

// 没有身份
assert_eq!(anonymous.status_code(), 401);

// 有身份，但没有资源权限
assert_eq!(non_owner.status_code(), 403);

不要把“没有 token”测成 403，也不要把“普通用户不能删别人的资源”测成 401；否则客户端无法决定是重新登录，还是显示权限不足。
