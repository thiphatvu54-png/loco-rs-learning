请求测试的数据边界：API、测试数据库和 fixture

目标：看懂 init_user_login 为什么同时调用 HTTP 和测试数据库，并学会把 Arrange / Act / Assert 分开。

1. 当前 helper 做了什么

pub async fn init_user_login(
    request: &TestServer,
    ctx: &AppContext,
) -> LoggedInUser {
    request.post("/api/auth/register").json(&payload).await;
    let user = users::Model::find_by_email(&ctx.db, USER_EMAIL).await.unwrap();
    request.post("/api/auth/verify").json(&verify_payload).await;
    let response = request.post("/api/auth/login").json(&login).await;
    LoggedInUser { user, token }
}

它不是生产逻辑，而是测试夹具。HTTP 请求验证“接口能工作”；直接查 ctx.db 是为了拿到 token、pid 或验证数据库状态。

2. 为什么查到的是“真的数据”

ctx.db 指向当前测试环境的数据库。这个项目的 test.yaml 默认使用独立 SQLite，并开启 dangerously_recreate / dangerously_truncate，所以每轮测试都从干净状态开始。

测试需要什么合适来源
验证接口返回TestServer 发 HTTP 请求
拿 pid、verification token测试数据库查询
验证写入结果测试数据库再次查询

这不是连接生产数据库；测试进程按 LOCO_ENV=test 读取 test 配置。

3. Arrange / Act / Assert

// Arrange：准备用户和 token
let logged_in = prepare_data::init_user_login(&request, &ctx).await;
let (key, value) = prepare_data::auth_header(&logged_in.token);

// Act：发出真实 HTTP 请求
let response = request
    .get("/api/auth/current")
    .add_header(key, value)
    .await;

// Assert：只断言这个测试关心的结果
assert_eq!(response.status_code(), 200);
边界原则：测试 helper 可以直接查测试数据库；生产 controller 不应该为了拿用户而绕过自己的业务边界直接读测试 helper。
