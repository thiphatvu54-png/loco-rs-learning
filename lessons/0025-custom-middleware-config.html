自定义 middleware 的配置边界

难点在这里：自定义 middleware 不是直接往 server.middlewares 里塞 YAML key，而是使用 Loco 的自由配置 settings:，再在 Hooks::middlewares 中构建它。

1. 配置放在 settings

# config/development.yaml
settings:
  admin_header:
    enable: true
    value: "admin-api-dev"

# config/production.yaml
settings:
  admin_header:
    enable: true
    value: "admin-api"

server.middlewares 是 Loco 已知内建 middleware 的强类型配置；应用自己的配置放到 settings，再用 ctx.config.settings::<T>() 解析。这样配置错误不会被静默吞掉。

2. 定义应用设置和 middleware

#[derive(Debug, Default, Deserialize)]
#[serde(default)]
struct AppSettings {
    admin_header: AdminHeaderSettings,
}

#[derive(Debug, Deserialize)]
#[serde(default)]
struct AdminHeaderSettings {
    enable: bool,
    value: String,
}

impl Default for AdminHeaderSettings {
    fn default() -> Self {
        Self { enable: false, value: "admin-api".into() }
    }
}

// MiddlewareLayer 的 AdminHeader 见上一课；这里把配置值传进去
fn middlewares(ctx: &AppContext) -> Vec<Box<dyn MiddlewareLayer>> {
    let settings: AppSettings = ctx
        .config
        .settings()
        .expect("invalid settings.admin_header");

    let mut stack = middleware::default_middleware_stack(ctx);
    stack.push(Box::new(AdminHeader {
        enable: settings.admin_header.enable,
        value: settings.admin_header.value,
    }));
    stack
}

3. 为什么不能直接写 server.middlewares.admin_header？

因为 server.middlewares 反序列化到 Loco 的固定 Server 配置结构；未知字段不会自动变成你的 Rust 类型。settings 是 Loco 明确提供的自由扩展槽，支持环境文件的深度合并。

4. 配置错误应该在哪里暴露？

位置特点
Hooks::middlewares 里 expect简单直接；配置错误在构建 middleware 时 panic
Hooks::after_context 或 load_config可以返回 Result，更适合生产启动失败

这是 API 边界：middlewares 本身返回 Vec，没有 Result；如果想优雅报告坏配置，就在更早的有错误返回值的 Hook 验证。
