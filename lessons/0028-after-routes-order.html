after_routes：谁最后包住 Router

难点是顺序：Loco 的默认 middleware 在 Routes::to_router 内先套上，之后才执行 Hooks::after_routes，最后才轮到每个 Initializer 的 after_routes。

1. 以当前源码为准的链

H::before_routes(ctx)
    ↓
H::routes(ctx).to_router(...)
    ├─ 注册 controller routes
    └─ 应用 H::middlewares(ctx)
    ↓
H::after_routes(router, ctx)
    ↓
initializer.after_routes(router, ctx)  // 按注册顺序
    ↓
serve

这意味着 Initializer 的 after_routes 是最后一个可改造 Router 的生命周期点。它适合挂诊断端点、追加 Axum layer，或把外部组件接到已经完成的路由图上。

2. 在 Initializer 中追加一个诊断 layer

use axum::{middleware, Router as AXRouter};
use loco_rs::{app::{AppContext, Initializer}, Result};

struct Diagnostics;

async fn mark_diagnostic(response: axum::response::Response)
    -> axum::response::Response
{
    response
}

#[async_trait]
impl Initializer for Diagnostics {
    fn name(&self) -> String { "diagnostics".into() }

    async fn after_routes(
        &self,
        router: AXRouter<AppContext>,
        _ctx: &AppContext,
    ) -> Result<AXRouter<AppContext>> {
        Ok(router.layer(middleware::map_response(mark_diagnostic)))
    }
}

这个 layer 在默认 Loco middleware 之外再包一层。响应离开 handler 时，先经过 initializer 的 layer，再经过之前的默认栈。

3. 和 Hooks::after_routes 的区别

扩展点适合顺序
Hooks::after_routes应用只有一段全局 Router 改造逻辑默认 middleware 后
Initializer::after_routes可独立启用、可健康检查的模块化组件Hooks after_routes 后，按注册顺序
Routes::layer单个 Routes/controller 组路由组内部

4. 注册多个 Initializer 时的顺序

Ok(vec![
    Box::new(AuditInitializer),
    Box::new(Diagnostics),
])

调用顺序是 AuditInitializer.after_routes → Diagnostics.after_routes。后一个 initializer 对 Router 的包装更外层，因此入站请求先看到 Diagnostics。
